# altkdf-rs (DeckTLS)

Experimental Rust implementation of **draft-sullivan-tls-xof-schedule**.
The TLS 1.3 cipher suite selects the AEAD; a separate `schedule_profile`
extension selects SHAKE256 or TurboSHAKE256 for the transcript hash and key
schedule, including Finished and PSK binders.

This version tracks the collaborative repository's `main` at
[`c6c02fb`](https://github.com/grittygrease/draft-sullivan-tls-xof-schedule-collab/blob/c6c02fbc45e5febbbc958068b4599e06f01f1dc0/draft-sullivan-tls-xof-schedule.md),
which includes PRs #2 through #15.
DeckTLS is this implementation's prototype name, not a protocol name.
The earlier `xof-ciphers-00` design and its `0xFF01..05` suites are obsolete.

**Research prototype, not production TLS.** The construction's security analysis
remains open. Matching vectors and successful handshakes are implementation
evidence, not a security proof or a FIPS approval.

## Layout

| Path | Scope |
|---|---|
| `deck-schedule/` | `no_std` + `alloc` core; one dependency, `zeroize` |
| `rustls-integration/` | Vendored rustls 0.23.41 fork, provider and config helpers |
| `tls-demo/` | TCP client/server, KeyUpdate, exporter and key-log checks |
| `deck-schedule/vectors/` | 162 fixed appendix values with source provenance |

The core implements Init/Absorb/Derive/DeriveN/Ratchet, the three-stage schedule,
record keys, the XOF MAC, RFC 9258 PSK import, exporters, resumption, ECH
derivations, DTLS record-number keys and Exported Authenticator fixtures.

The fork negotiates the KDF in ClientHello, ServerHello and HelloRetryRequest.
Both KDFs work with AES-128-GCM, AES-256-GCM and ChaCha20-Poly1305 over
ML-KEM768, X25519, secp256r1 and the hybrid groups X25519MLKEM768 and
SecP256r1MLKEM768. Hybrid component secrets are absorbed separately, in the
group's concatenation order. Tests cover all six AEAD/KDF pairs, HRR, 1-RTT
resumption, accepted 0-RTT, imported external PSKs, KeyUpdate and exporters.
XOF PSKs bind a KDF rather than an AEAD, so 1-RTT resumption may change AEAD
under the same KDF; early data is then rejected, as the draft requires.
Ordinary HKDF resumption retains upstream's exact-suite policy.

Experimental identifiers are extension **0xffa6** and KDFs **0x0100/0x0101**.
They are local interoperability conventions, not IANA assignments.

## Build And Test

```sh
cargo test
make ci        # fmt, clippy, tests, vectors, count, no_std and strict docs
make reproduce # compare all 162 fixed appendix values
make bench     # minimal schedule graph, not a runtime benchmark
```

The appendix expectations are extracted from the pinned specification, not
generated by the Rust implementation under test. Primitive KATs cover SHAKE256
and TurboSHAKE256. Tests need no sibling specification checkout.

The minimal representative schedule measures **15 XOF calls / 23 permutations**,
versus **30 HMAC/HKDF calls / 120 permutations** for HKDF-SHA3-256. The SHAKE256
comparison uses the same 24-round Keccak permutation. It excludes transcript
hashing and post-handshake derivations. The stage API and live adapter recompute
some joint outputs, so these figures are not the live handshake's call count
or a measured speedup.

## TCP Demo

Run in two terminals:

```sh
SSLKEYLOGFILE=/tmp/deck-server.keylog cargo run -p tls-demo --bin deck-server
SSLKEYLOGFILE=/tmp/deck-client.keylog cargo run -p tls-demo --bin deck-client
```

Both default to `127.0.0.1:4443`; pass a port as the first argument to each.
The endpoints print the selected suite, KDF, group, ALPN and exporter value.

The demo client accepts any certificate chain while checking CertificateVerify.
It is deliberately insecure and must not be used for real connections.
Key logs contain traffic secrets; do not publish them.
NSS-format logs alone do not enable stock Wireshark to decrypt this experimental
schedule. See [the demo README](tls-demo/README.md).

## Scope And Limits

- Config helpers require an XOF KDF and enable 1-RTT resumption. Early data is
  off by default; opt in through `ClientConfig.enable_early_data` and
  `ServerConfig.max_early_data_size`.
- Imported external PSKs support DHE handshakes. The client offers one identity
  for its first XOF KDF; HRR can retain or remove it, never replace it.
- DTLS, Exported Authenticators, raw external PSKs and PSK-only handshakes have
  core/vector coverage, not live stack integration.
- The client can offer XOF KDFs with ECH and checks both acceptance
  confirmations under the KDF the server selects. An ordinary server's
  rejection completes the outer handshake. There is no ECH server here, so
  accepted ECH has not been tested live. Imported external PSKs with ECH are
  refused before ClientHello.
- QUIC has no XOF mapping. Unknown key-exchange groups, and known hybrids
  without component boundaries, are refused under an XOF KDF.
- Mixed XOF/HKDF providers support fallback, but selection can fail if the
  chosen KDF has no usable AEAD. The default XOF provider avoids this case.
- Some low-level helpers panic on out-of-range caller-supplied lengths.
  The integration uses fixed, valid lengths.
- The server session encoding includes the KDF and does not accept tickets
  from the earlier experimental design.

Live accumulator buffers, their growth, squeezed secrets and stage state are
zeroized on drop where the implementation controls storage. Erasure is best
effort; reference/vector outputs intentionally use ordinary byte vectors.
